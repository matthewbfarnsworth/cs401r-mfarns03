## ADR-001: NorthStar Platform Foundation

### Status
Accepted

### Context
NorthStar Retail is a specialty retailer with 400 stores across North America and an e-commerce presence contributing 28% of revenue. NorthStar faces an annual $128.5M customer churn problem: approximately 18% of its 2.1M active customers churn annually, representing an estimated lifetime value loss of $340 per customer. To reduce churn toward a target of 14%, Chief Data Officer Maya Chen has commissioned a unified AI platform shared across three systems:

1. **Churn Prediction Model**: A weekly batch model scoring 2.1M customers to identify 90-day churn risks before Monday 6 AM ET, directing retention offers to the top 10% highest-risk segment.
2. **Offer Generation (LLM / RAG)**: A real-time system generating personalized retention incentives under 2 seconds to replace generic 20% discounts and increase redemption rates from 6% to 12%.
3. **Customer Service Agent**: An autonomous agent handling 50% of 14,000 daily routine inquiries to reduce human escalation handle times by 30%.

These workloads process store point-of-sale transactions, Shopify webhooks, CRM records, and 90,000 clickstream events/hour. NorthStar must protect customer Personal Identifiable Information (PII) and ensure data governance from day one. Allowing engineers administrative access or flat storage access risks accidental corruption of historical records and training models on unverified features. An established identity model and tiered storage layout are required from the outset to ensure auditability, reliability, and data integrity.

### Decision
We established the platform foundation using a dedicated Amazon VPC network boundary, tiered Amazon S3 storage, and a least-privilege AWS IAM identity structure.

1. **VPC Topology**: We deployed a dedicated VPC (`northstar-dev-vpc`) with CIDR `10.0.0.0/16`, DNS enabled, and a public subnet (`10.0.100.0/24`) in `us-east-1a`. SageMaker Studio deploys into this VPC. A security group (`northstar-dev-sagemaker-sg`) restricts inbound traffic strictly to the VPC CIDR (`10.0.0.0/16`), denying public inbound access. Egress routes through an Internet Gateway (`northstar-dev-igw`) for container pulls and AWS API communication.
2. **Tiered S3 Storage Architecture**: We provisioned a data bucket (`northstar-dev-data-{account_id}`) with AES-256 encryption, versioning enabled, and public access blocked. The bucket contains four logical stages:
   - `raw/`: Source transactions from store POS, Shopify webhooks, and clickstream data.
   - `processed/`: Cleaned and standardized data generated by automated ETL pipelines.
   - `features/`: Engineered feature tables utilized directly for model training and inference.
   - `artifacts/`: Exported model weights, training checkpoints, and evaluation results.
3. **IAM Least-Privilege Role Model**: We created the `northstar-dev-MLEngineer` role assumed by SageMaker Studio. This role has explicit permissions to read and write objects exclusively within `features/` and `artifacts/`. Write permissions to `raw/` and `processed/` are denied by omission, preventing ML practitioners from altering ground-truth records.

### Consequences
#### What this makes easy
- **Data Lineage and Auditability**: Machine learning pipelines consume only validated data from `features/`. Model outputs stored in `artifacts/` are auditable against training feature sets.
- **Controlled Collaboration**: Data engineers and ML engineers operate within designated operational boundaries, enabling parallel development without risk of overwriting pipeline outputs.

#### What this makes harder
- **Immediate Pipeline Failure Mode**: If an ML script attempts to write intermediate datasets or logs into `raw/` or `processed/`, the job halts immediately with an AWS IAM `AccessDenied` (HTTP 403) exception.
- **Networking Environment Constraints**: Placing SageMaker Studio inside a public subnet satisfies Lab 1 development requirements, but does not provide complete network isolation. It requires migrating to private subnets with a NAT Gateway (introducing an additional ~$32–$45/month operational cost) in Lab 2 before connecting to internal retail databases.

#### What would cause you to revisit this decision
- **S3 Prefix Throughput Limits**: If peak clickstream volume from NorthStar web and mobile applications exceeds 90,000 events/hour and approaches S3 prefix request rate limits (3,500 PUT or 5,500 GET requests per second), we will partition prefixes using date or hash keys.
- **Production Scale and Enterprise Connectivity**: Scaling to production serving for 2.1M active customers and 14,000 daily support inquiries will necessitate transitioning from a single public subnet to a multi-AZ private topology with VPC endpoints and private network peering.

### Alternative Considered
We evaluated deploying **Separate S3 Buckets** for each lifecycle stage (`northstar-dev-raw`, `northstar-dev-processed`, `northstar-dev-features`, and `northstar-dev-artifacts`) rather than logical prefixes within a single bucket. 

This alternative presents clear benefits: it establishes physical isolation in AWS, allows S3 Object Lock on compliance data, simplifies retention lifecycles (24-month raw data retention vs. 90-day feature expiration), and enables spend tracking for CFO Robert Hess.

**Rejection Rationale**:
We rejected separate buckets due to pipeline complexity, policy fragmentation, and operational overhead:

1. **Pipeline Copy Overhead**: Transforming data from `raw` to `processed` and generating `features` across separate buckets requires cross-bucket object copying. This incurs unnecessary API copy requests, introduces synchronization latency, and duplicates storage during execution. Prefix partitioning within a unified bucket allows streamlined transformations under a consistent namespace.
2. **Policy Fragmentation**: Every separate bucket requires its own bucket policy, CORS configuration, Public Access Block, and KMS key policy. Across Dev, Staging, and Prod environments, NorthStar would manage 12 independent buckets. Pipeline roles must maintain extensive lists of bucket ARNs, increasing the risk of configuration drift and permission gaps.
3. **Operational Naming Sprawl**: S3 bucket names must be globally unique across all AWS accounts. Managing 12+ globally unique names adds friction in Terraform automation. A single bucket provides a clean security perimeter.

Prefix-level IAM conditions provide the exact same access restrictions required to protect customer PII without multi-bucket sprawl.

### AWS Service Selection
- **Networking isolation model**: Amazon VPC provides network isolation using private `10.0.0.0/16` CIDR blocks to ensure ML notebooks and training instances are inaccessible from the public internet.
- **Storage design**: Amazon S3 provides 99.999999999% durability and granular prefix-level access control to enforce our four-tier data lifecycle within a centralized storage boundary.
- **Identity model**: AWS IAM provides role-based least privilege access control that prevents machine learning roles from modifying raw or processed enterprise data.
- **ML development environment**: Amazon SageMaker Studio provides a fully managed JupyterLab environment that attaches natively to our VPC and automatically assumes our scoped execution role.
